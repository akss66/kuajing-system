## 5. 不得改变的业务不变量

### 订单、金额与库存

- 拿货单只是一个店铺一次导出的订单集合；包裹/平台订单才是履约和每包运费的边界。
- 每个包裹收取物流费 ¥13；非 `TZX` SKU 不收商品货款，但仍收该包裹 ¥13，并正常进入极风履约。
- 下单锁定库存；极风确认发货后正式扣减；取消时释放对应未发货包裹的库存占用。
- 已取消拿货单不计入有效订单数量与金额，但必须保留历史、资金流水、库存流水和审计证据。
- 父拿货单与子包裹需要支持独立状态查询、取消、重试、释放和退款处理；整单操作必须聚合子包裹结果，不能假装原子成功。
- 价格使用订单快照，后续货盘改价不得污染历史订单。
- 重复导入、重复点击、第三方重投、Worker 重跑必须幂等；并发更新必须使用事务、唯一约束或 CAS 防止双扣和重复退款。

### SKU 导入与替换

- `-lk` / `-LK` 是平台后缀，可忽略后精确匹配标准 SKU。
- `2PCS` 表示发两件，必须正确换算最终发货数量。
- 缺货时默认只展示同一商品系列的替代 SKU，同时允许手工输入最终 SKU 和修改数量。
- 非 `TZX` SKU 仍需进入履约；如果极风接口可验证 SKU 是否存在，应在提交前验证，但不得因此错误收取商品货款。

### 极风

- 按平台订单号匹配极风已有订单，禁止为已存在订单重复新建。
- 已匹配但尚未提交仓库时，客户/运营文案应为：
  - `待在极风后台提交仓库`
  - `已匹配到极风订单，请在极风后台选择物流渠道并提交仓库；系统随后自动同步。`
- 当前确认由人工在极风后台选择物流渠道并提交仓库；系统通过轮询/回调继续同步状态、Canada Post 单号和发货结果。
- 暂时性查询失败不能立刻升级为永久运营异常；必须区分可重试和永久错误，正确维护退避、`nextRetryAt`、租约、claim token、CAS、死信、通知和审计。

### 飞书过渡

- 飞书源表始终只读，`FEISHU_CARGO_WRITES_ENABLED` 必须保持 `false`。
- 目前仍处于约一周人工维护过渡期，允许从飞书单向镜像到系统；不得反写飞书。
- 过渡期结束后，系统数据库正式承接货盘并成为唯一事实来源；届时应关闭/移除人工飞书同步入口，但保留迁移审计记录。

### 权限与数据隔离

- `SUPER_ADMIN` 拥有全部权限，主要负责系统正常运行和系统维护。
- 普通 `ADMIN` 拥有客户创建、客户状态、付款、库存、履约、退款等正常业务权限，但不拥有系统维护能力。
- 客户账号必须按 `customerId` 隔离，只能访问自己的店铺、订单、余额、商品价格和相关 PII。
- 任何错误信息、日志、通知或 UI 都不得暴露 token、数据库细节、内部堆栈、其他客户 PII 或系统内部错误码。

## 6. 产品与 UI 已确认方向

- 客户端应是 macOS / 现代 SaaS 的独立客户端体验，而不是传统运营 Dashboard。
- 使用浅冷灰主背景、白色内容面、翡翠绿品牌色、大圆角、克制阴影和高密度长条列表。
- 货盘使用高密度长条行，不使用巨大商品卡片；图片需要懒加载、稳定占位和可接受的首屏速度。
- 上传页面支持显眼的大面积拖放；控件必须对齐，原生退化下拉框需要统一设计。
- 个人中心整合账号、所属客户、可操作店铺和资金概览；避免突兀的深色孤立卡片。
- 动效只用于状态反馈、进入/退出和可操作性提示；尊重 `prefers-reduced-motion`，不得以动效掩盖加载延迟。
- 管理端与客户端使用各自的设计文档和信息架构，但共享基础 token 与无障碍标准。
