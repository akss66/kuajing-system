# ADR-001：极风履约只匹配已有订单

## 状态

已接受

## 日期

2026-08-21

## 背景

极风订单由仓库侧预先建立。本系统中的拿货单是一次 TEMU 导出的订单集合，每个子包裹保存 TEMU 包裹订单号。若本系统再次调用极风创建接口，可能产生重复订单、错误库存占用和难以判定的取消竞态。

## 决策

- 本系统不提供、也不调用极风创建订单接口。
- 每个普通包裹使用 `order_shipments.external_order_no`，每个补发包裹使用其系统生成的 `REPL-*` 外部订单号，作为极风 `platformOrderNo` 精确查询。
- 查询结果的 `platformOrderNo` 必须与本地包裹完全相同；极风真实 `erpNo` 还必须在系统内保持唯一绑定。
- 未找到订单是等待状态，按退避计划继续匹配，不展示为仓库异常。
- 匹配成功后只轮询、取消和接收回调；库存仍以系统数据库为事实来源，并在极风确认发货后正式扣减。
- 数据库中的事件名 `JIFENG_CREATE_ORDER` 和幂等键 `jifeng:create:<shipmentId>` 暂时保留，仅用于兼容历史 Outbox 行，不能解释为允许创建订单。

## 备选方案

### 由本系统创建极风订单

拒绝。该方案与仓库现行流程冲突，并在网络超时、重复点击或双方同时建单时产生重复履约风险。

### 先按本地临时 ERP 号查询

拒绝。极风已有订单的 ERP 号不由本系统控制；TEMU 包裹订单号才是双方约定的稳定关联键。

### 模糊匹配或使用子订单商品行号

拒绝。一个包裹可以包含多条商品行，模糊或行级匹配可能把一个远端订单绑定到错误包裹。

## 后果

- 极风客户端和运行时不再暴露创建订单能力，也不再向极风发送收件人 PII、商品或价格用于建单。
- 运营需要先确保极风已有完全相同的平台订单号；暂未建单时系统会自动等待。
- 补发单也必须先使用系统显示的 `REPL-*` 号在极风建好对应订单。
- 将来若要改变该规则，必须新建 ADR，并同时设计历史 Outbox 数据迁移、幂等边界和重复订单防护，不能只恢复一个 API 方法。
