# 上传订单多货品映射实施计划

## 架构决定

- 保留 `order_import_rows` 作为上传源行和第一项最终货品的兼容载体，新增不可混淆的“当前客户自有 SKU”字段，并用子表保存第二项及后续货品。
- 订单明细增加同一平台子订单内的稳定位置，使一个子订单可生成多条有效明细，同时继续按子订单去重。
- 所有库存与金额计算先把第一项和新增项展开为统一的领域集合，再复用现有价格、库存和包裹逻辑。

## 任务

### 第一阶段：数据契约

- [ ] 添加上传行最终客户 SKU、附加货品表和订单明细位置字段的前向迁移。
  - 验收：历史预览与历史订单保持可读；数据库约束拒绝空 SKU、非正数量和模式/系统 SKU 不一致。
  - 验证：迁移集成测试、`npm.cmd run typecheck`。
  - 依赖：无。

- [ ] 增加统一的预览货品读取模型。
  - 验收：每行至少返回第一项货品，附加货品按稳定位置返回；原 SKU 与最终 SKU 明确分离。
  - 验证：order-import 预览集成测试。
  - 依赖：数据契约。

### 第二阶段：编辑与校验

- [ ] 让第一项货品可在系统 SKU 与客户自有货之间安全切换。
  - 验收：非 TZX 可改为另一非 TZX 或 TZX；原 SKU 不变；旧版本写入被 CAS 拒绝。
  - 验证：服务集成测试和 Action 单元测试。
  - 依赖：统一读取模型。

- [ ] 增加附加货品的新增、修改和删除。
  - 验收：客户隔离、最多 20 项、自由文本校验、TZX 可售/价格校验和删除后的库存重算全部生效。
  - 验证：服务集成测试。
  - 依赖：第一项切换。

### 检查点：预览领域层

- [ ] order-import 针对性单元与集成测试通过。
- [ ] 迁移可从当前 schema 单向应用。

### 第三阶段：提交、金额与导出

- [ ] 单店提交展开全部最终货品。
  - 验收：混合货品分别计价，库存汇总锁定，包裹和运费不增加，原 SKU 写入每条订单明细。
  - 验证：orders submission 集成测试。
  - 依赖：编辑与校验。

- [ ] 批量提交与工作区汇总展开全部最终货品。
  - 验收：多店库存冲突、预计金额、结算总额和幂等行为与单货品规则一致。
  - 验证：bulk-order validation/submission/workspace 集成测试。
  - 依赖：单店提交。

- [ ] 极风导出按最终货品拆行。
  - 验收：每行重复不可变原 SKU，并输出各自最终 SKU 和数量。
  - 验证：Jifeng unit/integration 测试。
  - 依赖：订单明细多行。

### 第四阶段：客户界面

- [ ] 预览编辑器增加“加一个货”、逐项保存和删除。
  - 验收：状态文案明确区分系统货与客户自有货；键盘、错误播报、44px 触控和移动端无溢出。
  - 验证：组件单元测试、客户预览 E2E、360/390/430px 截图检查。
  - 依赖：服务端编辑能力。

### 最终检查点

- [ ] 完整 unit、serial integration、E2E、typecheck、lint、production build、dependency audit 和 diff-check 全部通过。
- [ ] 只读复核确认无客户越权、非 TZX 计费、库存绕过、重复运费或原 SKU 覆盖。
- [ ] 原子提交并推送 GitHub；门禁通过后合并 `main`，本任务不部署。

## 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 同一子订单多行破坏现有唯一约束 | P0 | 增加稳定行位置并保留以子订单为单位的去重查询 |
| 附加 TZX 未进入库存汇总 | P0 | 单店与批量提交均以展开后的统一货品集合做集成测试 |
| 客户伪造模式或价格 | P0 | 服务端只接收 SKU 文本和数量，重新推导模式并读取价格 |
| 原 SKU 被编辑覆盖 | P1 | 服务方法禁止更新 `external_sku`，导出集成测试固定语义 |
| 增加货品导致重复运费 | P1 | 包裹仍只从原始上传行的平台订单号去重生成 |
