# 极风 WMS OAuth 安全接入设计

日期：2026-08-13  
状态：设计已口头确认，待书面规格复核  
范围：极风开发者配置、OAuth 授权、令牌安全存储、仓库与加拿大邮政渠道发现、只读诊断、履约启用门

## 1. 背景与目标

同舟行跨境已经具备极风订单创建、查询、取消、状态同步和异常重试的基础客户端，但当前依赖静态环境变量提供 `accessToken`、`refreshToken`、`userId`、仓库编码和物流渠道。管理员现在已经拿到极风开发者名称、`client_id` 和 `client_secret`，还没有完成用户 OAuth 授权。

极风官方文档明确区分开发者凭据和用户授权信息：首次授权需要先获取授权码，再兑换 `accessToken`、`refreshToken` 和 `userId`；`accessToken` 有效期约 24 小时，过期后用长期 `refreshToken` 刷新。所有业务接口使用 POST JSON，并在请求头携带开发者、用户和 HMAC-SHA256 签名信息。

本次目标：

1. 超级管理员在系统后台完成极风 OAuth 授权，无需把访问令牌粘贴到环境变量或聊天中。
2. 开发者 ID 和密钥只保存在服务器密钥环境中；授权令牌加密后保存在 PostgreSQL。
3. 授权完成后只执行只读探测，自动发现可用仓库和加拿大邮政物流渠道。
4. 在超级管理员明确启用履约前，系统不得向极风创建、取消或更新任何真实订单。
5. 授权、刷新、选择资源、诊断、启用、停用和断开连接都必须可审计、可恢复且不泄露秘密。

本次不做：

- 不把极风库存作为系统货盘库存来源。
- 不自动启用真实推单。
- 不在 UI、日志、审计记录或错误消息中展示完整令牌、开发者密钥或 OAuth 授权码。
- 不把“开发者名称”当作鉴权参数；它只作为后台展示信息。
- 不猜测生产 API 域名。生产基础 URL 必须由极风提供并通过服务器环境配置。

## 2. 方案选择

采用“服务器开发者凭据 + 数据库加密 OAuth 令牌 + 显式履约启用门”的方案。

比较过的方案：

1. **推荐方案：OAuth 令牌加密入库。** 支持自动刷新、权限收口、审计和后台状态展示，适合长期运行。
2. **全部静态环境变量。** 实现简单，但令牌轮换需要人工改环境并重启服务，无法形成完整授权审计，不作为最终方案。
3. **接入外部密钥管理服务。** 安全上限更高，但当前部署只有单台 Ubuntu 服务器和独立 PostgreSQL，增加新的基础设施暂时没有必要。数据库字段使用应用层信封加密，未来可以平滑迁移到 KMS。

旧的静态令牌配置只保留为短期兼容读取路径，不在新 UI 中提供录入入口。数据库中存在有效 OAuth 连接时必须优先使用数据库连接；静态配置不得覆盖它。完成生产授权验收后，再单独安排静态令牌兼容路径的移除。

## 3. 权限与信任边界

- 只有 `super_admin` 可以开始授权、查看连接详情、运行远程诊断、选择仓库/物流渠道、启用履约、停用履约和断开连接。
- 普通管理员只能看到“极风连接是否可用、履约是否启用、最近一次同步状态”等非敏感运行状态，不可触发授权或更改配置。
- OAuth 回调不依赖当前浏览器会话授权，而依赖一次性、短时有效、绑定发起超级管理员的 `state`。回调完成后记录原发起人。
- 开发者 ID、开发者密钥和令牌加密主密钥只存在服务器环境变量中，不进入数据库。
- 数据库仅保存加密后的 access/refresh token、非敏感授权主体 ID、资源选择和连接状态。
- 浏览器只接收授权跳转 URL、非敏感状态和脱敏错误，不接收任何令牌明文。

## 4. 配置边界

服务器环境变量：

- `JIFENG_BASE_URL`：极风确认的生产 API 基础 URL。
- `JIFENG_CLIENT_ID`：开发者 ID。
- `JIFENG_CLIENT_SECRET`：开发者密钥。
- `JIFENG_OAUTH_REDIRECT_URI`：固定为生产回调地址，例如 `https://shop.tzxai.top/api/integrations/jifeng/oauth/callback`。
- `JIFENG_TOKEN_ENCRYPTION_KEY`：独立的 32 字节随机密钥，使用受控编码格式加载。

可选展示配置：

- `JIFENG_DEVELOPER_NAME`：仅用于后台展示，不参与签名或 OAuth 请求。

禁止：

- 不允许从页面录入或回显 `client_secret`、加密主密钥。
- 不允许生产环境用请求参数覆盖 `JIFENG_BASE_URL` 或回调地址。
- 不允许把回调地址从不可信的 `Host`、`Origin` 或转发头动态拼接出来。

## 5. 数据模型

### 5.1 `jifeng_connections`

系统只维护一个当前连接记录，但不依赖数据库“只有一行”的脆弱约定；通过固定连接键和唯一约束保证单例。

核心字段：

- `id`、固定 `connection_key`
- `status`：`DISCONNECTED`、`AUTHORIZED`、`RESOURCE_SELECTION_REQUIRED`、`READY_DISABLED`、`ENABLED`、`REFRESH_REQUIRED`、`ERROR`
- `user_id`
- access token 密文、refresh token 密文
- 每个密文对应的加密版本、随机 nonce/IV 和认证标签，或一个版本化信封字段
- access token 到期时间、refresh token 到期时间（极风未返回精确值时按官方有效期保守计算）
- `warehouse_code`
- `logistics_id`
- 资源显示名称快照
- `authorized_by_admin_user_id`
- `authorized_at`、`last_refreshed_at`、`last_diagnostic_at`
- `last_error_code`、脱敏 `last_error_summary`
- `fulfillment_enabled_at`、`fulfillment_enabled_by_admin_user_id`
- `created_at`、`updated_at`

明文令牌绝不进入普通查询 DTO。解密函数只对极风客户端凭据提供者开放。

### 5.2 `jifeng_oauth_states`

- `state_digest`：只保存随机 state 的 SHA-256 摘要
- `initiated_by_admin_user_id`
- `expires_at`
- `used_at`
- `created_at`

原始 state 只交给浏览器和极风。回调必须在同一数据库事务中锁定 state 记录、验证未使用且未过期，并原子标记 `used_at`，防止重放。

### 5.3 审计日志

写入现有 `audit_logs`：

- `JIFENG_OAUTH_STARTED`
- `JIFENG_OAUTH_AUTHORIZED`
- `JIFENG_TOKEN_REFRESHED`
- `JIFENG_RESOURCES_SELECTED`
- `JIFENG_DIAGNOSTIC_RUN`
- `JIFENG_FULFILLMENT_ENABLED`
- `JIFENG_FULFILLMENT_DISABLED`
- `JIFENG_DISCONNECTED`

审计 metadata 只记录状态、资源标识、错误分类和请求 ID，不记录令牌、授权码、签名或完整第三方响应。

## 6. OAuth 与连接流程

### 6.1 开始授权

1. 超级管理员点击“开始授权”。
2. Server Action 再次执行 `requireSuperAdmin()`。
3. 生成至少 256 bit 的随机 state，只保存摘要，默认 10 分钟过期。
4. 使用固定配置的极风授权端点、`client_id`、回调地址和原始 state 构造跳转 URL。
5. 写入开始授权审计，浏览器跳转到极风。

同一管理员可重新开始授权；旧未使用 state 可以自然过期。回调只能消费与自己携带 state 对应的单条记录。

### 6.2 OAuth 回调

1. 严格校验 `code` 和 `state` 的格式与长度。
2. 事务内锁定并消费 state；不存在、已使用或过期立即失败。
3. 服务器向极风令牌端点兑换授权信息。
4. 校验响应结构和必要字段，不信任未知字段。
5. 使用 AES-256-GCM 和独立随机 nonce 加密 access/refresh token。
6. 原子更新连接记录为 `AUTHORIZED`，记录授权主体和时间。
7. 写入审计后跳转回后台集成页；URL 和页面不得保留 code/state。

如果 state 已经合法消费但令牌兑换失败，连接保持原有可用状态（如果存在），并记录一次脱敏失败。管理员可重新发起授权。

### 6.3 令牌刷新

- 每次业务请求前检查 access token 的保守过期时间，临近过期时刷新。
- 并发刷新使用数据库行锁或等价单航班机制，避免多个 worker 同时刷新。
- 刷新成功后原子替换密文和到期时间；使用新令牌继续原请求。
- 明确的授权失效将连接置为 `REFRESH_REQUIRED`，关闭新的履约领取，不盲目重试。
- 网络、限流和 5xx 使用已有受控退避语义，不把暂时故障误判为永久断开。

## 7. 仓库与加拿大邮政渠道发现

授权成功后执行只读发现：

1. 调用极风仓库列表/详情接口，读取当前授权用户可用仓库。
2. 调用客户物流渠道接口，读取可用的线下物流渠道。
3. 使用名称、承运商代码和服务名称识别加拿大邮政候选项，但不只依赖模糊文本。
4. 如果仓库与加拿大邮政渠道各只有一个明确候选，预选并展示给超级管理员确认。
5. 如果存在多个候选、没有候选或字段无法可靠识别，状态进入 `RESOURCE_SELECTION_REQUIRED`，由超级管理员在后台选择。
6. 保存资源标识和显示名称快照；每次启用前重新验证资源仍然可用。

不得为了“自动完成”而静默选择第一个仓库或第一个物流渠道。

## 8. 只读诊断

诊断分两级：

1. **本地自检**：检查配置分层和官方签名样例，永不联网、不使用真实订单。
2. **远程只读探测**：使用专用、确定不会与业务订单冲突的 ERP 单号调用订单查询；官方“订单不存在”结果视为鉴权和签名链路可用，其他结果按认证、限流、网络、业务拒绝分类。

远程诊断不得调用创建、取消、更新或库存调整接口。页面显示：配置层级、授权状态、令牌健康、资源选择、最后诊断时间和脱敏结果。

## 9. 履约启用门

极风连接和极风履约是两个独立状态。

只有同时满足以下条件，超级管理员才能点击“启用真实履约”：

- 开发者配置完整。
- OAuth 授权有效且可刷新。
- 仓库和加拿大邮政渠道已明确选择并通过只读验证。
- 最近一次远程诊断成功。
- 超级管理员在确认对话框中明确确认“启用后，已付款待发货订单可被推送到极风”。

worker 在领取任何极风创建/取消任务前都必须读取数据库连接状态并确认 `ENABLED`，不能只依赖进程启动时的环境变量。停用只阻止新的第三方调用，不伪装撤回已经到达极风的订单；已有不确定状态继续走查询/对账流程。

## 10. 断开、重新授权与故障恢复

- **停用履约**：保留授权和资源选择，立即阻止新推单，允许只读查询和必要对账。
- **重新授权**：成功后替换令牌，但保留资源选择；重新验证资源后才恢复 `READY_DISABLED` 或 `ENABLED`。
- **断开连接**：先停用履约，再清除令牌密文、用户 ID 和资源选择，状态变为 `DISCONNECTED`。断开操作不可撤销，必须二次确认并填写原因。
- **加密密钥不可用或密文认证失败**：连接进入 `ERROR`，禁止履约，不尝试使用损坏凭据。
- **数据库写入失败**：不报告授权成功；不把只存在内存中的令牌继续用于业务请求。

## 11. UI 设计

后台“外部集成”中的极风卡片分为：

- 当前状态：未配置、待授权、待选择资源、已连接未启用、已启用、需重新授权、异常。
- 非敏感配置：开发者名称、开发者 ID 脱敏值、API 域名、回调地址。
- 授权信息：授权时间、授权操作人、用户 ID 脱敏值、令牌健康；不显示令牌内容。
- 资源选择：仓库和物流渠道下拉列表及刷新按钮。
- 诊断：本地自检、远程只读测试、最近结果。
- 操作：开始/重新授权、启用/停用履约、断开连接。

所有危险操作使用明确后果文案。普通管理员页面只读；超级管理员才看到操作入口。移动端不使用横向溢出的宽表格。

## 12. 测试策略

### 单元测试

- 开发者配置、运行时配置和数据库授权配置的优先级。
- AES-256-GCM 加解密、随机 nonce、错误密钥和篡改密文拒绝。
- state 摘要、过期、一次性消费和格式校验。
- OAuth URL 和 token 响应校验。
- 仓库/加拿大邮政候选识别与歧义阻断。
- 连接状态机、启用条件和脱敏错误映射。

### PostgreSQL 集成测试

- 只有超级管理员可发起和管理授权。
- state 并发回调只能成功一次。
- 令牌刷新并发只有一次远程刷新，其他请求复用结果。
- 旧连接在新授权兑换失败时不被破坏。
- 授权、资源选择、启停和断开审计不含秘密。
- `ENABLED` 以外状态下 worker 不领取或调用极风任务。
- 停用与正在进行的创建/查询并发时遵循既有安全边界。

### 端到端测试

- 超级管理员完成模拟 OAuth、选择资源、只读诊断和启用。
- 普通管理员无法看到或调用管理动作。
- 回调 state 无效/过期/重放时展示安全的中文错误。
- 390px 移动端能查看状态并完成授权后的资源确认。

真实极风验收只使用只读接口。第一次真实订单推送必须作为独立、明确批准的验收步骤，不包含在 OAuth 接入自动化测试中。

## 13. 部署与上线顺序

1. 部署数据库迁移和 OAuth/凭据提供者代码，但保持履约关闭。
2. 在服务器交互式配置开发者 ID、密钥、生产基础 URL、固定回调地址和令牌加密密钥。
3. 重启新项目容器，验证敏感环境不出现在页面、日志和容器镜像层。
4. 在极风后台登记完全一致的 HTTPS 回调地址。
5. 超级管理员发起授权。
6. 完成仓库/加拿大邮政渠道确认和只读诊断。
7. 保持 `READY_DISABLED`，先观察令牌刷新和只读查询。
8. 经业务负责人单独确认后启用真实履约，并使用一张受控测试订单验收。

回滚时先停用履约；应用回滚不能删除连接表和审计记录。旧静态令牌兼容路径只用于短期应急，不自动恢复真实推单。

## 14. 完成标准

1. 超级管理员可从系统发起并完成极风 OAuth，普通管理员不可操作。
2. 数据库、日志、审计、页面和错误信息中不存在令牌或密钥明文。
3. access token 可在并发环境下安全刷新；refresh token 失效会要求重新授权。
4. 仓库和加拿大邮政渠道可发现、可确认，歧义不会被静默接受。
5. 只读诊断可以证明签名、鉴权和订单查询链路可用，且不会创建任何订单。
6. 未显式启用时，worker 不会调用极风写接口。
7. 启用、停用、重新授权和断开连接均有准确审计和可理解的中文反馈。
8. 现有订单创建、查询、取消、状态同步和对账的安全语义不被削弱。
