# 货盘可售状态筛选设计

日期：2026-08-15
状态：已确认

## 目标

在管理端“商品与 SKU”和客户端“货盘选品”中增加统一的 SKU 状态筛选，让用户可以快速查看全部、可售或不可售货品，同时保持“一个飞书序号对应一个商品、商品下包含多个 SKU”的分组结构。

## 筛选口径

页面提供三个互斥选项：

- `全部`：显示当前搜索结果中的全部 SKU。
- `可售`：只显示符合可售条件的 SKU。
- `不可售`：只显示不符合可售条件的 SKU。

管理端按 SKU 的 `saleStatus` 判断：`SELLABLE` 为可售，`NOT_SELLABLE` 为不可售。

客户端按真实可下单结果判断：`availabilityReason === "AVAILABLE"` 为可售；`MANUALLY_UNAVAILABLE` 与 `SOLD_OUT` 都归入不可售。客户端仍保留原有“不可售”和“售罄”具体徽标，不把两种原因混成同一业务状态。

## 分组、搜索与状态的组合规则

处理顺序固定为：

1. 按 `productId` 将 SKU 组成商品组。
2. 文本搜索匹配商品或任一 SKU；命中任一 SKU 时先保留完整商品组。
3. 在搜索结果内应用状态筛选，只保留符合状态的 SKU。
4. 移除筛选后没有任何 SKU 的空商品组。

因此，搜索 `TZX-001-2` 时仍能看到该商品全部兄弟 SKU；若随后选择“可售”，则该商品组内只保留可售兄弟 SKU。这能同时满足商品上下文查找和实际选品筛选。

结果计数始终反映当前可见结果，例如 `12 个商品 / 19 个 SKU`，而不是筛选前总数。

## 界面

沿用现有货盘工具栏，在搜索框附近增加带明确标签的三段式单选控件或等价单选按钮组：`全部`、`可售`、`不可售`。不增加新侧栏、新页面或高级筛选抽屉。

- 桌面端：控件与搜索框同一工具区，宽度不足时自然换行。
- 移动端：控件占一整行，三个选项均保持至少 44px 触控高度。
- 当前选项有清晰的选中状态，不能只依赖颜色表达。
- 控件使用单选语义并提供可访问名称“销售状态筛选”。
- 空结果文案应说明当前搜索或状态条件没有匹配项，并提供恢复到“全部”的明确操作或提示。

不改变商品表格、商品卡片、SKU 链接、价格、库存、权限和下单行为。

## 状态与数据流

筛选状态仅存在于当前页面会话，不写数据库、不改变 SKU 状态，也不触发服务端 mutation。首版不写入 URL 查询参数，刷新后恢复为“全部”。

管理端和客户端可共享一个纯函数完成组内 SKU 状态筛选，但各自传入自己的可售判断函数，避免把管理端 `saleStatus` 与客户端库存可用性混为一谈。

## 验证

单元测试覆盖：

- 默认“全部”显示所有 SKU。
- “可售”只保留可售 SKU，并移除空商品组。
- “不可售”包含人工不可售和售罄 SKU。
- 混合状态商品在筛选后仍只有一个父商品组。
- 文本搜索命中一个 SKU 后，状态筛选按上述顺序作用。
- 结果计数与当前可见商品/SKU 一致。
- 客户页面不暴露采购价、货品价格、总库存或飞书序号。

浏览器测试覆盖管理端和客户端的桌面、430、390、360 宽度，验证无文字重叠、页面横向溢出、hydration/console 错误或 axe serious/critical 问题。

## 非目标

- 不增加多选状态、价格区间、库存区间或保存筛选方案。
- 不把筛选条件写入数据库或飞书。
- 不改变 `SELLABLE`、`NOT_SELLABLE`、`AVAILABLE`、`MANUALLY_UNAVAILABLE`、`SOLD_OUT` 的业务定义。
- 不新增购物车、数量输入或拿货单提交能力。
